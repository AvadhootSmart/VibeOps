# SSH Tools — how they were implemented and why

The deploy feature needs the agent to run commands on remote servers. The
local `shellAccess` tool *could* shell out to `ssh`, but that breaks in
exactly the ways that matter inside a webview:

1. **No TTY.** A password prompt or the "authenticity of host … (yes/no)?"
   host-key prompt blocks forever, and the agent freezes with it.
2. **No state.** One `ssh host cmd` per command means a full handshake every
   time, and `cd /app` in call 1 is forgotten by call 2.
3. **No timeout.** `ShellAccess` has no deadline, so a hung remote command
   hangs the whole tool call.

So SSH got its own service with three methods: `Connect`, `RunRemote`,
`Disconnect`. Everything fragile (auth, host verification, connection
lifetime, timeouts) lives in Go where it can fail fast with a clear error;
the model only ever passes strings around.

## The two-layer bridge (same pattern as every VibeOps tool)

An AI tool spans Go and TS:

```
model → tools/index.ts (name)  →  tools/ssh.ts (schema + execute)
      → wailsjs/go/tools/ssh   →  Wails IPC  →  backend/tools/ssh.go
```

Files touched:

| File | Role |
|---|---|
| `backend/tools/ssh.go` | The `SSH` service struct: real SSH via `golang.org/x/crypto/ssh` |
| `main.go` | `sshSvc := tools.NewSSH()` added to the `Bind` list |
| `frontend/wailsjs/go/tools/ssh.js/.d.ts` | Generated by Wails from the Go signatures — never hand-edited |
| `frontend/src/lib/ai/tools/ssh.ts` | Three `tool({...})` definitions with model-facing docs + zod schemas |
| `frontend/src/lib/ai/tools/index.ts` | Registered as `sshConnect`, `sshRun`, `sshDisconnect` |

Binding a struct in `main.go` is what makes Wails generate the TS namespace;
`wails dev` regenerates it whenever the Go signatures change.

## Go side design decisions

### Session registry

```go
type SSH struct {
    mu      sync.Mutex
    clients map[string]*ssh.Client
}
```

One `*ssh.Client` is one live TCP+SSH connection. The map is keyed by a
human-readable session ID, `user@host:port` (e.g. `root@1.2.3.4:22`), instead
of a UUID — the model can *read* it, and reconnecting to the same server
naturally replaces the old entry instead of leaking connections. The mutex
exists because Wails may run binding calls concurrently.

### Connect: fail fast instead of prompting

- **Auth is key-file only.** `keyPath == ""` tries `~/.ssh/id_ed25519` then
  `~/.ssh/id_rsa` — the same defaults `ssh` itself uses. Passphrase-protected
  keys are detected via `*ssh.PassphraseMissingError` and rejected with a
  message that says why; anything else would need an interactive prompt we
  can't show.
- **Host keys are verified** against `~/.ssh/known_hosts` using
  `golang.org/x/crypto/ssh/knownhosts`. This is the one place we refused to
  be lazy: `ssh.InsecureIgnoreHostKey()` is one line and silently accepts
  man-in-the-middle servers. The tradeoff: an unknown server errors and tells
  the user to `ssh` in once from a terminal (which records the host key).
- **`Timeout: 10 * time.Second`** on the dial so an unreachable host errors
  in 10s instead of hanging on TCP.

### RunRemote: one connection, many commands

`client.NewSession()` is cheap — it multiplexes a new channel over the
already-open connection, no new handshake. Each session is a fresh remote
shell, which means **`cd` and env vars don't persist between calls**. That's
inherent to SSH exec channels; rather than hide it with a stateful PTY
emulation, the tool description tells the model to chain state:
`cd /app && git pull && make`.

Two deliberate output choices:

1. **Non-zero exit is not a Go error.** Wails delivers a Go `error` as a
   promise rejection, which would *discard the command's output* — and for
   deploys, the output of a failing command is the whole point. So the exit
   error is appended to the output as `[command failed: ...]` and the call
   returns `nil`. Go errors are reserved for tool-level failures (bad
   session, timeout).
2. **120s timeout.** `ssh.Session` has no context support, so the command
   runs in a goroutine and a `select` races it against `time.After`; on
   timeout `sess.Close()` tears down the channel (killing the remote
   process) and the model gets told the command was killed. This is why the
   tool doc says to background long-running processes.

If `NewSession` fails, the connection itself is dead (server rebooted,
network dropped) — the client is closed and removed from the map so the
model gets "session is dead — reconnect" instead of repeated cryptic
failures.

### Disconnect

Close, delete from map, done. Calling it on an unknown ID errors harmlessly.

## TS side: the docs ARE the interface

The model never sees the Go code — its entire understanding of these tools is
the `description` strings in `ssh.ts`. They encode every sharp edge as an
instruction:

- host-key failure → "tell the user to ssh in once, don't retry"
- fresh shell per call → "chain state with `&&`"
- 120s kill → "background long-lived processes"
- `[command failed: ...]` → "the command failed, not the tool"
- dead session → "reconnect and retry once"

Each zod field has a `.describe()` with an example value, so even weak
OpenRouter models produce well-formed calls. This is the guardrail argument
for having SSH tools at all: the schema does the thinking that bash-only
would leave to the model.

## Deliberately skipped (add when it bites)

- **ssh-agent auth** — would support passphrase keys; add via
  `golang.org/x/crypto/ssh/agent` when a user actually has one.
- **SFTP/file upload** — `sshRun` with heredocs, or local `scp` via
  `shellAccess`, covers deploys for now.
- **Streaming output** — `CombinedOutput` returns everything at the end; a
  live-streaming variant needs Wails events and UI work. Worth it once
  deploys routinely exceed a few seconds of output silence.
- **Configurable timeout** — 120s is hardcoded; make it a parameter when a
  legitimate command (big `npm install`?) first hits it.
